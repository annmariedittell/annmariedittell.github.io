Case Study

Evaluating and Resolving an Accessible Date Picker

Looking beyond a WCAG failure to understand task completion, severity, and systemic impact.

My Role
Accessibility testing
Focus
Keyboard + screen reader UX
Severity
Major
Scope
Shared component

Challenge

During accessibility testing, I identified several barriers in a shared calendar and date-picker component used across multiple application screens.

  • Generic accessible names that made date controls difficult to distinguish
  • Limited keyboard navigation
  • Unexpected focus movement when changing months
  • Month and year changes that were not announced to screen reader users

How I Thought Through the Problem

IdentifyExperienceAssess ImpactDetermine SeverityFind Root CauseRemediateRetestValidate

Can the user identify the control? A label such as “Calendar” may technically provide an accessible name, but it does not necessarily tell the user which date field it belongs to.

Can the user operate it without a mouse? Opening the calendar is only the first step. Users also need a clear and predictable way to navigate dates and calendar controls.

Does focus behave predictably? Unexpected focus movement can disorient users who rely on keyboard navigation or cannot visually track where focus has moved.

Can the user still complete the task? Although the date picker had significant barriers, users could still manually enter a date in the associated field.

Severity and Systemic Impact

Because users had an alternative way to complete the task, I classified the issue as Major rather than Critical. The workaround did not make the component accessible, but it meant users were not completely blocked.

I also recognized that this was a shared component issue. Addressing the underlying component could improve the experience everywhere it was used, instead of repeatedly fixing the same defect on individual screens.

Solution and Validation

The remediation needed to address descriptive accessible names, keyboard support, predictable focus behavior, screen reader notification of dynamic changes, and support for manual date entry.

After the component was updated, I retested the interaction using keyboard and screen reader testing to confirm that the accessibility issues were resolved.

Outcome

  • Improved the experience for keyboard and screen reader users
  • Reduced the chance of the same defect recurring across the application
  • Created more consistent date-picker behavior
  • Reduced repeated remediation effort
Key takeaway: Accessibility testing is more than identifying a failed WCAG requirement. I focus on what the user is trying to accomplish, where the experience breaks down, how serious the impact is, and whether the issue is isolated or systemic.
